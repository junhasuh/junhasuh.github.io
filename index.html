Python 배포 조율기를 팀 NestJS 백엔드로 이식

2026.09.28~10.04 · 소프트뱅크 해커톤 · 6인 팀

Hibiscus는 기록된 HTTP 요청으로 앱을 검증하고, 정책 판단·승인·서명을 거친 이미지를 Cloud Run 또는 온프레미스에 배포하는 서비스입니다. 하이브리드 배포 방향을 제안하고 배포 조율·롤백·GCP 인프라를 맡았습니다.

팀 백엔드의 배포 단계로 통합

Python으로 만든 배포 조율기를 NestJS로 옮겼습니다. 팀의 검증·정책·서명 결과를 받아, 대상별 클라이언트와 대표 경로 전환 기능을 통해 배포를 진행하도록 연결했습니다.

현재 배포에 대한 서명인지 먼저 확인

cosign 공개키 검증과 함께 이미지 저장소·식별값(digest), 실행 ID·정책 결정 해시를 대조했습니다. 잘못된 이미지나 다른 실행의 서명이면 후보 생성 전에 중단하도록 했습니다.

재시도와 이미지 추적을 고려한 Cloud Run 스크립트

이미지 식별값과 배포 ID로 배포 버전(revision) 이름을 만들어 같은 배포의 재시도에서 기존 버전을 재사용했습니다. 멀티 아키텍처 이미지의 원본 식별값도 별도로 남겨 추적할 수 있게 했습니다.

01 / HIBISCUS · 설계 판단과 실패 복구

Hibiscus Cloud Run·온프레미스 순차 전환

새 버전은 양쪽에 트래픽 0%로 먼저 띄우고, 둘 다 헬스 검사를 통과해야 전환합니다. 한쪽만 새 버전이 되는 상태를 막으려고, 한쪽만 실패해도 배포 전체를 보류하는 쪽을 택했습니다. 전환 순서는 Cloud Run → 온프레미스 → 대표 경로입니다. Cloud Run은 트래픽을 이전 revision으로 돌리기만 하면 되돌릴 수 있어 먼저 바꿨고, 사용자가 보는 대표 경로는 마지막에 바꿔 두 환경의 전환 시차가 드러나지 않게 했습니다.

Hibiscus PR #26 팀원 리뷰 결함 수정

문제
팀원이 리뷰에서 재현해 지적한 결함: 경로 전환이 실패해도 activated로 남고 롤백이 호출되지 않았습니다.
수정
경로 전환이 실패하면 Cloud Run은 이전 revision으로, 온프레미스는 이전 컨테이너로 되돌리고 rolled_back으로 기록하게 고쳤습니다. 되돌릴 컨테이너가 없으면 error로 남겨 수동 처리합니다.
검증
단위 테스트 3개와 통합 테스트 1개를 추가하고 다른 팀원의 승인을 받아 병합했습니다.

02 / 영주로그 · 개인 CI/CD 확장

영주로그 Jenkins·Kubernetes 파이프라인 구축

2026.09 구축·검증 기록 · Jenkins / Ansible / Kubernetes / SonarQube

영주로그는 영주시의 역사 탐방 서비스입니다. 팀 프로젝트에서 EC2·RDS 배포와 도메인 연결을 맡았고, 이후 팀 백엔드를 포크해 개인적으로 CI/CD를 구축했습니다.

테스트 환경과 운영 설정 분리

CI 테스트는 H2 데이터베이스와 테스트용 설정으로 실행하도록 구성했습니다. 운영 설정은 환경변수로 분리하고, 이미지에 커밋 해시를 붙여 배포 버전을 구분했습니다.

새 파드가 요청을 받을 준비가 됐는지 확인

Deployment 매니페스트에 readinessProbe와 롤링 업데이트(maxSurge 1, maxUnavailable 0)를 설정했습니다. 배포 때는 Ansible이 kubectl set image로 이미지 태그만 바꾸고, 새 파드가 준비 상태가 돼야 기존 파드를 내립니다.

EC2 Docker 헬스체크와 Kubernetes readinessProbe

EC2 Docker 배포 때는 DB와 상관없이 UP을 주던 /v1/health 대신 /actuator/health를 6초 간격으로 최대 20번 확인했습니다. 운영 DB 환경변수를 뺀 커밋에서 이 확인이 실패해 직전 이미지(cfe545d)로 돌아갔습니다. Kubernetes로 옮긴 뒤 readinessProbe는 /actuator/health/readiness를 봅니다.

03 / 기반 역량 · Terraform 실습 및 CKA 기출 풀이

Terraform으로 구성한 AWS 네트워크·IAM과 CKA 기출 장애

Terraform AWS 네트워크·IAM 구성

VPC·퍼블릭/프라이빗 서브넷·인터넷/NAT 게이트웨이·라우팅과 EC2용 IAM 역할·인스턴스 프로파일을 코드로 구성했습니다. IAM·S3 실습의 상태 파일은 S3 원격 백엔드로 옮기고 DynamoDB 테이블로 잠금을 걸었고, VPC 디렉터리는 로컬 상태로 남아 있습니다.

발생
Terraform이 상태를 새로 읽다가(Refreshing state) iam:GetRole에서 AccessDenied
단서
직전에 ~/.aws/credentials를 지웠는데 다른 AWS 명령은 계속 동작
확인
aws sts get-caller-identity 결과가 IAM 사용자가 아니라 assumed-role
원인
자격 증명 파일이 사라지자 체인의 마지막인 인스턴스 메타데이터로 내려가, s3·dynamodb 권한만 있는 인스턴스 역할로 실행됨
조치
콘솔에서 역할에 조회 권한을 붙인 뒤 같은 코드로 통과

CKA 준비 중 기출 문제로 풀어본 장애

파드가 Pending에 머무는 상황

kubectl describe node의 Allocated resources로 이미 잡힌 요청량을 보고, Allocatable에서 뺀 여유가 새 파드의 요청보다 작다는 걸 확인했습니다. 스케줄러는 실사용량이 아니라 선언된 요청량을 봅니다.

API 서버가 응답하지 않는 상황

journalctl -u kubelet로 kubelet 로그를 보고, kube-apiserver 정적 파드의 --etcd-servers가 etcd의 advertise-client-url과 다른 IP를 가리키던 것을 고쳤습니다.

CKA를 딴 뒤(2026.08) 영주로그를 Kubernetes로 옮기며 롤링 업데이트·readinessProbe·rollout undo를 직접 설정했습니다. 인스턴스 프로파일은 Terraform으로 만들어 봤지만, 영주로그 앱은 아직 S3 접근에 액세스 키를 환경변수로 받습니다. EC2 IAM 역할로 바꾸는 게 남은 일입니다.
