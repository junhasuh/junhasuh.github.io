시험 설계 이유 (Why 503?)

왜 장애 시험에서 온프레미스 Agent API만 503으로 차단했는가?

이미 Cloud Run이 새 버전으로 넘어간 뒤 온프레미스 전환 단계에서 실패했을 때 Cloud Run까지 다시 이전 버전으로 롤백되는지를 시험해야 했습니다.

  • • 앱 헬스 체크를 500으로 만들면 안 되는 이유: 전환 단계까지 가지도 않고 맨 앞의 '트래픽 0% 후보 검증 단계'에서 걸러져 배포가 보류(held)되므로 롤백 로직을 시험할 수 없습니다.
  • • Agent API에 401/403을 주면 안 되는 이유: 인증 실패 코드를 받으면 온프레미스 Agent 프로세스가 스스로 종료되도록 구현되어 있었습니다(Agent 코드 97~100행 ↗).
  • • 해결(Agent API만 47초간 503 반환): 후보 검증이 끝난 직후 앞단 Caddy 리버스 프록시에서 Agent 폴링 API만 503으로 막아 Agent가 재시도하다가 전환 기한(30초)을 초과하게 만들었고, 그 즉시 Cloud Run이 이전 Revision으로 자동 복귀하는 것을 확인했습니다.
협업 및 코드 품질 개선 (PR #26)

대표 경로 전환 실패 시 롤백이 누락되던 상태 기록 순서 결함 수정

Python 조율기를 NestJS로 이식(PR #26 ↗)할 당시, 팀원의 코드 리뷰(리뷰 코멘트 ↗)를 통해 마지막 단계의 예외 처리 결함을 발견하고 보완했습니다.

[원인] Cloud Run과 온프레미스 전환 직후 배포 상태를 activated(성공)로 먼저 기록하고 그 뒤에 사용자 대표 경로(Gateway)를 변경해, 정작 대표 경로 전환이 실패해도 롤백이 호출되지 않았습니다.
[해결 및 테스트 검증] 대표 경로 전환까지 마친 뒤에야 성공으로 기록하도록 순서를 바로잡고, 실패 시 양쪽 환경을 동시에 이전 버전으로 되돌린 뒤 rolled_back(복구 대상이 없으면 error)으로 기록하게 수정했습니다.

설계 판단 (Why fail after rescue?)

롤백이 성공했는데도 왜 Jenkins 빌드를 FAILURE로 끝냈는가?

Ansible에서 rescue 블록으로 rollout undo만 실행하고 끝내면, 복구 작업 자체가 성공했기 때문에 종료 코드가 0이 되어 Jenkins 빌드가 초록불(SUCCESS)로 표시되는 문제가 있었습니다. 개발자가 배포 실패 사실을 즉시 인지할 수 있도록 복구 직후 fail 모듈을 호출해 의도적으로 빌드를 FAILURE로 남겼습니다(k8s-deploy.yml 11~17행 ↗).

Terraform · AWS 자격 증명 체인 TROUBLESHOOTING #1 ↗

~/.aws/credentials 삭제 후 iam:GetRole만 AccessDenied가 발생한 문제

[단서 및 원인] 로컬 자격 증명 파일을 지웠는데도 S3·DynamoDB 명령은 계속 동작하고 iam:GetRole에서만 권한 오류가 났습니다. aws sts get-caller-identity로 현재 실행 주체를 조회한 결과, 자격 증명 체인의 마지막 단계인 EC2 인스턴스 메타데이터 역할(IMDS assumed-role)로 자동 전환되어 S3·DynamoDB 권한만 가진 상태로 실행되고 있음을 밝혀냈습니다.
[조치] 전체 관리자 권한을 주는 대신 작업 서버의 인스턴스 역할에 필요한 IAM 조회 권한만 추가해 해결했습니다.

Terraform · 리소스 생성 순서(DAG) TROUBLESHOOTING #2 ↗

IAM 사용자 생성 전에 그룹 멤버십이 먼저 실행되어 NoSuchEntity (404) 발생

[원인] aws_iam_group_membership에 사용자 이름을 단순 변수 문자열(var.user_names)로 넘기면, Terraform이 사용자 리소스와의 선후 의존 관계를 알지 못해 그룹 연결을 먼저 시도하다가 404 오류가 발생했습니다.
[조치] 문자열 변수 대신 생성된 IAM 사용자 리소스의 속성(aws_iam_user.this[*].name)을 직접 참조하도록 수정해 암시적 의존성으로 생성 순서를 보장했습니다(devops_group.tf 5~11행 ↗).

Kubernetes · 컨트롤 플레인 복구 CKA 실습

kubectl 명령어가 먹통이 된 API 서버 무응답 장애 복구

[단서 및 원인] API 서버가 죽어 kubectl을 쓸 수 없는 상황에서 journalctl -u kubelet으로 노드 데몬 로그를 먼저 추적했습니다. 그 결과 kube-apiserver 정적 파드 매니페스트의 --etcd-servers 주소가 실제 etcd 설정(advertise-client-urls)과 다른 IP를 가리켜 연결이 거부되고 있음을 확인했습니다.
[조치] 정적 파드 매니페스트의 etcd IP를 실제 주소와 일치시켜 클러스터 제어를 즉시 복구했습니다.

DinD(Docker-in-Docker) 환경에서 배포한 컨테이너 포트 접속 불가 해결

[원인 및 조치] 컨테이너 내부의 독립 Docker 데몬(DinD)에서 앱 컨테이너를 띄우면 호스트 네트워크와 격리되어 외부 브라우저에서 접근할 수 없었습니다. 호스트의 /var/run/docker.sock을 공유하는 DooD(Docker-out-of-Docker) 구조로 전환해 호스트 레벨에서 컨테이너와 포트를 일관되게 관리하도록 개선했습니다. (공군 전산장비정비병 복무 시절에도 스위치 포트 → 서버실 패치 패널 → T568B 랜 케이블 직접 제작·결선 테스터 확인 순으로 계층별 원인을 좁혀 해결했습니다.)
