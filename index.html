1

왜 배포 직전에 cosign 서명을 다시 검증했는가?

  • • Why: 컨테이너 이미지 태그만으로는 앞단의 HTTP Replay 검증과 Policy 승인을 통과한 이미지인지 보장할 수 없었습니다.
  • • How: 배포 시작 전 cosign verify로 공개키 서명을 확인하고, 이미지 digest와 run_id, plan_hash가 일치할 때만 Candidate 컨테이너를 띄우도록 차단 관문을 구현했습니다.
2

왜 Python 프로토타입을 NestJS 백엔드로 이식했는가?

  • • Why: 해커톤 초기 빠른 검증을 위해 Python으로 배포 스크립트를 먼저 작성했으나, 팀의 메인 백엔드(NestJS)와 DB 상태 관리·Webhook 파이프라인·에러 처리를 일원화해야 했습니다.
  • • How: Orchestrator를 NestJS 모듈로 재설계하여 On-Premise Agent API 클라이언트와 Gateway 라우팅 전환을 단일 흐름으로 묶고, Vitest로 Rollback 분기 단위·E2E 테스트를 구축했습니다.
3

왜 Cloud Run → On-Premise → Gateway 순으로 전환했는가?

  • • Why: 두 환경의 배포 완료 시점이 다를 때 한쪽만 구버전인 상태로 트래픽이 섞이거나, 중간 실패 시 복구가 꼬이는 현상을 방지해야 했습니다.
  • • How: 양쪽 모두 트래픽 0% Candidate 상태에서 Health Check를 통과한 뒤에만 전환을 시작합니다. Revision 비율 조정만으로 즉시 복구 가능한 Cloud Run을 먼저 전환하고, On-Premise 전환까지 완료된 후 마지막에 Gateway Route를 바꿉니다.

Fault Injection Design (Why 503?)

왜 On-Premise Agent API만 503으로 차단했는가?

Cloud Run이 먼저 새 버전으로 전환된 직후, On-Premise 전환 단계에서 실패했을 때 Cloud Run까지 직전 버전으로 정확히 Rollback되는지 검증해야 했습니다.

  • • 컨테이너 Health Check를 500으로 만들지 않은 이유: 전환 단계에 진입하기 전 앞단의 '트래픽 0% Candidate 검증 단계'에서 걸러져 보류(held)로 끝나므로 부분 전환 후 Rollback을 시험할 수 없습니다.
  • • Agent API에 401/403을 주지 않은 이유: 인증 실패 응답 시 On-Premise Agent 프로세스가 즉시 종료되도록 설계되어 있었습니다.
  • • Agent API만 47초간 503 차단: Candidate 검증 통과 직후 Caddy에서 Agent Polling 경로만 503으로 차단해 전환 Timeout(30초)을 유도했고, 선전환됐던 Cloud Run이 이전 Revision으로 자동 복귀하는 것을 실증했습니다.
Code Review & Defect Fix (PR #26)

Gateway Route 전환 실패 시 Rollback이 누락되던 상태 기록 결함 수정

Python Orchestrator를 NestJS로 이식할 당시 코드 리뷰 과정에서 마지막 단계의 예외 처리 결함을 발견해 수정했습니다.

Root Cause: Cloud Run과 On-Premise 전환 직후 배포 상태를 activated로 먼저 기록하고 그 뒤에 Gateway Route를 변경해, 정작 Route 전환이 실패해도 Rollback이 호출되지 않았습니다.
Fix & Verification: Gateway Route 전환까지 완료된 후 activated를 기록하도록 순서를 교정하고, 실패 시 양쪽 환경을 동시에 직전 버전으로 되돌린 뒤 rolled_back(복구 대상 부재 시 error)으로 기록하게 수정했습니다.

Troubleshooting 01 · Cloud Run Reserved Path

On-Premise에선 통과한 /healthz가 Cloud Run에서만 404를 반환한 이슈

동일한 이미지를 배포했는데 On-Premise Candidate는 통과하고 Cloud Run Candidate에서만 /healthz 요청이 3회 연속 404로 실패했습니다. 확인 결과 Cloud Run 프론트엔드가 /healthz 등 z로 끝나는 경로를 내부 예약 경로로 가로채 컨테이너까지 요청이 도달하지 않는 제약이 있었고, Orchestrator가 즉시 양쪽 후보를 정리(held)한 뒤 엔드포인트를 /health로 변경해 해결했습니다.

Troubleshooting 02 · Manifest Digest Mismatch

Docker 29 환경에서 Multi-arch Index Digest가 어긋나던 이슈

cosign으로 서명한 이미지 digest와 배포 단계에서 조회한 Registry digest가 일치하지 않아 서명 검증에서 거부되었습니다. GCP VM의 Docker 29 기본 containerd snapshotter 설정이 Multi-arch index manifest를 다르게 처리해 발생한 문제임을 확인하고, 스토리지 드라이버를 overlay2로 변경해 빌드·푸시 시점의 digest 일관성을 확보했습니다.

Cloud Run 표시 Digest(amd64)와 서명 Digest(index) 차이 해결

Pipeline Design · Explicit Failure

Rollback이 성공했는데도 왜 Jenkins 빌드를 FAILURE로 끝냈는가?

Ansible에서 rescue 블록으로 rollout undo만 실행하고 끝내면 복구 태스크 자체가 성공으로 처리되어 종료 코드 0을 반환하고, Jenkins 빌드가 SUCCESS로 잘못 표시되는 문제가 있었습니다. 배포 실패 사실을 즉시 인지할 수 있도록 복구 직후 fail 모듈을 호출해 빌드를 FAILURE로 마감했습니다.

✗ Root Cause: 신규 Pod의 requests.cpu > 노드의 잔여 Allocatable

kube-scheduler는 실제 CPU 사용량이 아니라 매니페스트에 선언된 requests 합계를 기준으로 노드를 배정합니다. 신규 Pod의 요청량이 노드 잔여 한계치를 초과해 UnexpectedAdmissionError 및 Pending 상태로 대기하고 있었습니다.

✓ Resolution: 노드 가용 한계치(Allocatable - Allocated) 이하로 Requests 조정

kubectl describe node로 확인한 가용 수치 범위 안으로 매니페스트의 requests.cpu를 하향 조정하고 kubelet을 재시작해 즉시 Running 전환을 확인했습니다.

Terraform · AWS Credential Chain IMDS assumed-role

~/.aws/credentials 삭제 후 iam:GetRole만 AccessDenied가 발생한 이슈

로컬 자격 증명 파일을 삭제했는데도 S3·DynamoDB 명령은 정상 동작하고 iam:GetRole에서만 권한 오류가 발생했습니다. aws sts get-caller-identity로 호출 주체를 확인한 결과, Credential Chain의 마지막 단계인 EC2 Instance Metadata Service(IMDS assumed-role)로 자동 전환되어 S3·DynamoDB 권한만 가진 채 실행되고 있음을 확인했고, 작업 서버 Role에 필요한 IAM 조회 권한만 최소한으로 추가해 해결했습니다.

Terraform · Resource Dependency (DAG) Implicit Dependency

IAM User 생성 전에 Group Membership이 먼저 실행되어 NoSuchEntity (404) 발생

aws_iam_group_membership에 사용자 이름을 단순 문자열 변수(var.user_names)로 전달하자, Terraform이 IAM User 리소스와의 선후 의존 관계를 파악하지 못해 그룹 연결을 먼저 호출하다가 404 오류가 발생했습니다. 문자열 변수 대신 생성된 리소스 속성(aws_iam_user.this[*].name)을 직접 참조하도록 수정해 DAG 생성 순서를 보장했습니다.

Kubernetes · Control Plane Recovery kubelet & etcd

kubectl 명령이 먹통이 된 kube-apiserver 무응답 장애 복구

API 서버가 중단되어 kubectl을 사용할 수 없는 상황에서 journalctl -u kubelet으로 노드 데몬 로그를 먼저 추적했습니다. 그 결과 kube-apiserver Static Pod 매니페스트의 --etcd-servers 주소가 실제 etcd 설정(advertise-client-urls)과 다른 IP를 가리켜 연결이 거부되고 있음을 찾아내어 매니페스트의 IP를 교정해 즉시 복구했습니다.

Docker · Jenkins Container Networking DinD → DooD

DinD 환경에서 배포한 컨테이너 포트 외부 접속 불가 해결

컨테이너 내부의 독립 Docker 데몬(DinD)에서 애플리케이션 컨테이너를 기동하면 호스트 네트워크와 격리되어 외부에서 접근할 수 없었습니다. 호스트의 /var/run/docker.sock을 마운트하는 DooD 구조로 전환해 호스트 레벨에서 컨테이너와 포트 바인딩을 일관되게 제어하도록 개선했습니다.
