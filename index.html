P2 / HIBISCUS ①

양쪽 후보가 모두 통과해야 순서대로 전환합니다

기간인원내 역할
2026.09.28~10.04 · 소프트뱅크 해커톤 20266명배포 단계(조율·부분 실패 롤백), GCP 실행 환경 구성, 팀 기능 연결

Hibiscus는 기록된 HTTP 요청으로 앱을 검증하는 배포 서비스입니다. 정책 판단·승인·서명을 거친 이미지만 Cloud Run이나 온프레미스에 배포합니다.

하이브리드 배포 방향은 제가 초기 회의에서 제안했습니다. 실무에서 쓰는 환경과 비슷하다고 봤습니다. 한쪽에 장애가 나면 다른 쪽으로 넘길 수 있다는 점도 이유였습니다. 처음에는 배포 조율기를 Python으로 따로 만들었습니다. 팀 백엔드가 NestJS로 다시 정리되면서 조율기를 백엔드의 배포 단계로 옮겼습니다.

P3 / HIBISCUS ②

온프레미스 전환을 일부러 실패시켜 Cloud Run 복귀를 확인했습니다

rolled_back은 전환이 시작된 뒤에 실패해야만 나오는 결과입니다. 일부러 만들지 않으면 확인할 방법이 없어서, 2026-10-03에 실제 Cloud Run·온프레미스 환경에서 시험했습니다.

실패를 만드는 방법

방법예상 결과선택
앱 헬스 검사가 500을 반환후보 검사에서 걸려 held로 끝남. 전환 단계까지 가지 않음쓰지 않음
Agent API가 401·403을 반환Agent가 스스로 종료함쓰지 않음
Agent API만 503으로 차단Agent가 재시도하는 사이 전환 작업이 30초 기한을 넘김사용

Agent가 401·403에서 종료하는 동작은 팀원이 작성한 Agent 코드 97~100행에서 확인했습니다.

온프레미스 후보가 통과한 직후 VM의 Caddy에서 Agent가 쓰는 API만 503으로 막았습니다. 공개 주소와 상태 확인은 SSH 터널로 가므로 이 차단의 영향을 받지 않습니다. Cloud Run 되돌리기가 끝난 뒤 차단을 풀었습니다(차단 47초).

이 수치를 읽는 법

  • 공개 주소는 약 1초마다 요청했습니다(109회). Cloud Run 상태는 약 5초마다 gcloud로 확인했습니다(26회).
  • 대표 경로는 테스트 전에 기록하고 테스트 뒤 콘솔에서 다시 확인했습니다. 경로는 그대로였습니다.
  • Cloud Run 상태는 5초 간격으로만 확인했습니다. 그래서 새 revision이 트래픽 100%를 받은 구간은 29~39초 범위로만 말할 수 있습니다.
  • 30초는 Agent 전환 작업의 기한입니다. 전체 복구 시간이 아닙니다.
  • 109건은 대표 경로를 바꾸기 전에 멈춘 이 시험 한 번의 관측입니다. 모든 배포의 무중단을 뜻하지 않습니다.
  • 같은 실패 경로는 단위 테스트로도 정의해 두었습니다.

PR #26: 팀원 리뷰에서 드러난 결함 수정

팀원이 리뷰에서 재현해 지적한 결함입니다. 대표 경로 전환이 실패해도 결과가 activated로 남고 롤백이 호출되지 않았습니다(리뷰 코멘트). 원인은 순서였습니다. 양쪽 전환이 끝난 시점에 이미 성공을 기록하고, 그 뒤에 대표 경로를 바꾸고 있었습니다.

대표 경로 전환이 실패했을 때수정 전수정 후(본인)
배포 기록activatedrolled_back
롤백호출되지 않음Cloud Run은 이전 revision으로, 온프레미스는 이전 컨테이너로 되돌림

되돌릴 컨테이너가 없으면 error로 남겨 수동으로 처리합니다. 이 경우를 다루는 단위 테스트 3개와 통합 테스트 1개를 추가했습니다(단위 테스트 287~350행, 통합 테스트 396~436행). 다른 팀원의 승인을 받아 병합했습니다(리뷰 승인, 수정 커밋).

P4 / HIBISCUS ③

GCP 실행 환경의 접근 경로와 권한을 구성했습니다

배포 단계가 실행될 백엔드 서버와 그 주변을 구성했습니다. 과정은 구축 회고 6절에 화면과 함께 정리했습니다.

백엔드는 Compute Engine VM에 올렸습니다. Agent SSH 터널 서버(TCP 2222), Docker 멀티 플랫폼 빌드, 상시 동작하는 작업 처리기, SQLite가 필요했기 때문입니다. 대신 VM이 단일 장애점이 됩니다.

기존 /v1/health는 DB가 살아 있든 죽어 있든 UP을 돌려줬습니다. Actuator는 DataSource가 있으면 DB 헬스 점검을 자동으로 등록합니다. 점검이 실패하면 전체 상태를 DOWN으로 바꾸고 HTTP 503을 반환합니다. 배포 확인 단계는 HTTP 상태 코드로 성공을 판단합니다. 그래서 DB 상태가 상태 코드에 반영되는 /actuator/health로 기준을 바꿨습니다.

Kubernetes로 옮긴 뒤 readinessProbe는 /actuator/health/readiness를 봅니다. 이 앱의 설정 파일에는 readiness 그룹 지정이 없어 Spring Boot 기본 구성을 따릅니다. 기본 readiness 그룹에는 DB 점검이 들어가지 않습니다. 그래서 기동한 뒤 DB 연결이 끊기는 상황은 readinessProbe가 잡지 못할 수 있습니다. 반대로 DB 점검을 readiness에 넣으면 DB 장애 때 파드가 모두 함께 빠질 수 있습니다. 넣을지는 두 경우의 위험을 비교해 정해야 합니다.

그 밖의 구성 판단

  • 이미지 태그는 latest 대신 커밋 해시를 씁니다. 지금 떠 있는 이미지가 어느 커밋인지 바로 추적할 수 있습니다.
  • 이미지는 Jenkins 서버에서 한 번만 빌드합니다. 앱 서버와 클러스터는 그 이미지를 받아 실행만 합니다.
  • CI 테스트는 H2와 더미 설정으로, 운영은 실제 DB와 환경변수로 나눴습니다. 그래서 운영 DB 설정 오류는 CI가 아니라 배포 확인 단계에서 잡혀야 했습니다(P6의 #7·#15).
  • EC2 Docker 단계에서는 Jenkins 서버와 앱 서버를 EC2 두 대로 나눴습니다. CI 서버에서 앱 서버로 들어오는 SSH는 IP 대신 CI 서버의 보안 그룹(ci-sg)을 출처로 허용했습니다. CI 서버 IP가 바뀌어도 규칙을 고칠 필요가 없습니다. 보안 그룹 참조는 사설 IP로 오는 트래픽에만 적용됩니다. Ansible도 인벤토리에 적은 사설 IP로 앱 서버에 접속합니다(inventory.ini 1~2행).
  • 운영 DB 접속 정보는 앱 서버의 env 파일(/opt/yeongjulog/app.env, 권한 600)에서 읽게 했습니다.

롤백 뒤에도 실패로 남긴 이유

롤백을 실행해도 배포 자체는 실패입니다. rescue만 두면 롤백이 성공했을 때 빌드도 성공으로 끝납니다. 그러면 개발자가 빌드 결과만 보고는 새 버전이 배포됐는지, 이전 버전으로 돌아갔는지 구별하기 어렵습니다. 그래서 rescue 마지막에 fail을 두어 롤백 뒤에도 빌드가 FAILURE로 남게 했습니다. 실패 메시지에는 어느 커밋이 실패했는지 나옵니다(k8s-deploy.yml 11~17행).

  • 서브넷과 NAT 게이트웨이를 같은 AZ에 두었습니다. 프라이빗 서브넷의 트래픽이 다른 AZ의 NAT를 거치면 요금이 붙기 때문입니다(vpc.tf 6~10행).
  • 라우트는 인라인 route {} 대신 aws_route 리소스로 통일했습니다. 같은 라우트 테이블에 두 방식을 섞으면 관리 대상이 충돌할 수 있기 때문입니다(README 40행).
  • EC2용 IAM 역할은 신뢰 정책(역할을 맡을 주체)과 권한 정책(허용할 작업)을 나눠 선언했습니다. 역할은 인스턴스 프로파일을 거쳐 EC2에 붙습니다(iam_role_hello.tf).
  • IAM·S3 실습의 상태 파일은 S3 원격 백엔드로 옮기고 DynamoDB 테이블로 잠금을 걸었습니다. VPC 디렉터리는 로컬 상태로 남아 있습니다.

연결과 남은 일

CKA를 딴 뒤(2026.08) 영주로그를 Kubernetes로 옮겼습니다. 이때 롤링 업데이트·readinessProbe·rollout undo를 직접 설정했습니다. 인스턴스 프로파일은 Terraform으로 만들어 봤지만, 영주로그 앱은 아직 S3 접근에 액세스 키를 환경변수로 받습니다. EC2 IAM 역할로 바꾸는 게 남은 일입니다. Terraform 저장소의 IAM 사용자 인라인 정책과 EC2 역할의 s3:*·dynamodb:* 권한도 아직 넓게 열려 있습니다. NAT 게이트웨이는 시간당 과금이라 상시 유지하지 않고 코드만 남겼습니다.
